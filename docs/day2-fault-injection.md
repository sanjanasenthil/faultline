# Faultline Day 2 Fault Injection

Date: 2026-10-10

## Goal

Make fault injection repeatable. Day 1 proved the demo and observability stack run. Day 2 adds:

- A first case catalog with 10 feature-flag incidents.
- A runner that validates case flags against the live demo before changing anything.
- Apply/reset commands for fault flags.
- Telemetry snapshot capture for later offline diagnosis.
- A simple decoy change log for future `recent_changes` tooling.

## Files

- `cases/day2_feature_flags.json` defines the first 10 cases.
- `scripts/cases.py` validates, applies, resets, runs, and snapshots cases.
- `runs/change-log.jsonl` is generated when a case has a decoy change.
- `snapshots/<case_id>/<timestamp>/` is generated by snapshot or run commands.

Generated `runs/` and `snapshots/` files are local experiment output and are ignored by Git.

## Case Set

The first set intentionally stays small and uses flags confirmed in the installed OpenTelemetry Demo:

| Fault flag | Variants used | Cases |
|---|---|---:|
| `adFailure` | `on` | 2 |
| `cartFailure` | `25%`, `50%`, `100%` | 4 |
| `paymentFailure` | `25%`, `50%`, `100%` | 4 |

Some cases include decoy deploy records. Those records are not real demo deploys; they are controlled red herrings for the future diagnosis agent.

## Commands

List cases:

```sh
python3 scripts/cases.py list
```

Validate case flags and variants against the live demo:

```sh
python3 scripts/cases.py validate
```

Apply one case:

```sh
python3 scripts/cases.py apply payment-failure-100-01
```

Reset Day 2 fault flags:

```sh
python3 scripts/cases.py reset
```

Capture a snapshot without changing flags:

```sh
python3 scripts/cases.py snapshot payment-failure-100-01
```

Apply a case, wait for telemetry, snapshot, and reset:

```sh
python3 scripts/cases.py run payment-failure-100-01 --hold-seconds 30
```

## Snapshot Contents

Each snapshot records:

- `metadata.json`: capture time and backend URLs.
- `case.json`: the ground-truth case definition.
- `flags.json`: the live flag configuration at capture time.
- `prometheus.json`: selected metrics, including trace-derived span call and error counts.
- `opensearch_logs.json`: recent OpenSearch log documents.
- `jaeger_ui_check.txt`: a lightweight check that the Jaeger UI is reachable.

The current demo version exposes Jaeger UI under `/jaeger/ui/`, but the old `/api/services` route returns 404. For now, snapshots use Prometheus `traces_span_metrics_calls_total` as machine-readable trace evidence and keep the Jaeger UI health check as confirmation that the trace UI is available.

## Verification Results

Validated 10 cases against the live flag API. Then ran:

```sh
python3 scripts/cases.py run ad-failure-on-01 --hold-seconds 3 --log-limit 5
```

Result:

- `adFailure=on` was applied.
- A snapshot was written under `snapshots/ad-failure-on-01/...`.
- The runner reset Day 2 fault flags to `off`.
- A final flag listing showed `adFailure`, `cartFailure`, and `paymentFailure` back at `off`.

## Learning Notes

A case is a controlled incident: it contains the exact fault we inject, the expected root service, the category, and the alert symptom. The diagnosis agent will not receive the fault field later; that field is ground truth for scoring. Snapshots are the bridge between live experimentation and repeatable evaluation: once captured, we can replay the same incident evidence without re-breaking the demo every time.
